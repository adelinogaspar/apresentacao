Três Bash, um só espírito

O Bash é o mesmo idioma nos três mundos. Muda o "apartamento", não a gramática.

Windows

Git Bash 🐧

Emulador do GNU que vem com o Git. Traz Bash, ls, grep, sed e todo o arsenal Linux dentro do Windows. Perfeito pra quem quer comandos Unix sem VM.

Linux

Bash nativo 🎌

O Bash de verdade, padrão em quase toda distro. É onde o Bash vive desde 1989 e onde tudo "simplesmente funciona".

macOS

Bash no Mac 🍎

A Apple trocou o shell padrão por zsh, mas o Bash continua lá (bem antigo, versão 3.2). Dá pra instalar um Bash moderno via Homebrew.

A sintaxe, os loops, os pipes, as funções e a variáveis são idênticos nos três Diferenças práticas: caminhos (\\ vs /), pacotes instalados e versão do Bash

Capítulo 2

~/.bashrc, o coração do terminal

Toda vez que você abre um terminal interativo, o Bash lê e executa este arquivo. Nele vivem aliases, funções, variáveis de ambiente e o PATH.

Como funciona

Executado a cada shell novo

Abriu terminal → o Bash roda o ~/.bashrc. Tudo que está lá dentro fica "sempre ligado": comandos que você inventou, atalhos, configurações.

Git Bash = Linux = macOS

Comportamento igual

É o mesmo arquivo e a mesma mecânica nos três. No Git Bash (Windows) e no macOS (quando você usa Bash), o ~/.bashrc é lido do home do usuário exatamente como no Linux. A única manha do macOS é que o zsh usa ~/.zshrc — mas se você pede Bash, é ~/.bashrc.

$ cat ~/.bashrc # aliases, funções e exports que todo terminal novo vai carregar $ echo 'alias ll="ls -l"' >> ~/.bashrc $ ▍

bootstrap.sh: só um portão

Dentro dele, apenas chamadas de source. Nada de lógica, nada de complicação.

#!/usr/bin/env bash # bootstrap.sh — arquivo principal BASH_HOME="$HOME/dev/bash" source "$BASH_HOME/java.sh" source "$BASH_HOME/maven.sh"
Por que isso é bom

Um ponto de entrada

O ~/.bashrc só precisa conhecer um arquivo. Quer adicionar um novo script? Um source a mais no bootstrap e pronto.

KISS

Legível em 10 segundos

Qualquer pessoa entende o bootstrap batendo o olho — e isso é exatamente o objetivo.

java.sh: Java certo, sem stress

Todas as versões ficam em ~/opt/java/jdk-<versão>. Um comando troca o Java do terminal na hora.

# java-set <version> → usa ~/opt/java/jdk-<version> java-set() { export JAVA_HOME="$HOME/opt/java/jdk-$1" export PATH="$JAVA_HOME/bin:$PATH" alias java="$JAVA_HOME/bin/java" alias keytool="$JAVA_HOME/bin/keytool" } # java-set-from-pom → lê a versão do pom.xml java-set-from-pom() { version=$(grep -oE ''<(java\.version|maven\.compiler\.(release|source))>[0-9]+' \ pom.xml | head -n 1 | grep -oE '[0-9]+') java-set "$version" }
java-set

Variables + aliases na hora

Define JAVA_HOME, PATH e ainda aliasiza java e keytool apontando para o novo JAVA_HOME.

java-set-from-pom

O pom.xml manda

Procura o pom.xml no diretório atual, descobre a versão do Java do build e chama java-set. Acabou o "função na versão errada".

$ java-set 25 Java 25 ativado ✔ $ java-set-from-pom Java 17 ativado ✔ (achado no pom.xml)

Capítulo 6

maven.sh: build em um comando

mvn-build já acerta o Java, usa settings.xml se existir e aceita parâmetros extras. Base pra qualquer comando Maven.

# mvn-build [parâmetros extras...] mvn-build() { java-set-from-pom # garante o Java certo antes if [ -f settings.xml ]; then mvn clean package -s settings.xml "$@" else mvn clean package "$@" fi } # mvn-build-skip-tests [extras...] mvn-build-skip-tests() { mvn-build -DskipTests "$@" }
Inteligência simples

settings.xml automático

Se settings.xml está ao lado do pom.xml, o build já roda com -s settings.xml. Se não, segue normal.

Extensível

"$@" libera tudo

Parâmetros extras passam direto pro Maven: mvn-build -DskipTests, profiles, propriedades... o wrapper não limita nada.

Instalação em 4 passos — igual em Windows, Mac e Linux

A mesma estrutura de diretórios nos três sistemas. Git Bash no Windows resolve tudo igualzinho.

1mkdir -p ~/opt/{java,maven} ← base das versões
2mkdir -p ~/dev/bash ← onde os scripts vivem
3unzip bash-toolkit.zip -d ~/dev/bash ← descompacta bootstrap, java.sh e maven.sh
4grep -qxF 'source $HOME/bootstrap.sh' ~/.bashrc 2>/dev/null || echo 'source $HOME/bootstrap.sh' >> ~/.bashrc ← só adiciona se ainda não estiver lá
O truque do passo 4: grep -qxF verifica se a linha já existe (x = linha exata, q = silencioso). Se existe, não faz nada. Se não, o || eco adiciona. Sem duplicados, sempre.

Por que isso é uma festa?

Thread virtual custa poucos cientos de bytes, sai de cena quando espera I/O e volta quando pode rodar. Milhões delas sem drama.

Memória
threads de plataforma: 1–2 MB cada. Virtuais: poucos KB na heap.
Escala
de centenas para milhões de threads simultâneas.
Mesmo código
API Thread normal; nada de reescrever a aplicação.
I/O liberado
esperar rede ou disco não desperdiça um core inteiro.
